# 安全写回 SOP

写回是把审核后的候选内容变成正式知识，不是把 Agent 输出直接保存到主库。

## 何时用

- 新增或修改正式知识页。
- 查询结论要从 `queries/` 提升为概念、实体或对比页。
- 改动会影响链接、索引、日志或多个文件。

## 三步总览

1. **准备**：确认目标、权限、来源、冲突、备份和回滚方式。
2. **审查**：查看完整差异，逐项确认，不允许静默覆盖冲突。
3. **写入与验证**：人工批准后写入，检查结果，并维护 `index` 与 `log`。

## 详细清单

### 写入前

- [ ] 候选稿位于 `10-收件箱/写回候选/` 或受控审核区。
- [ ] 已确认目标文件允许修改；`raw/` 一律排除。
- [ ] 已记录支持来源、反对来源和同名实体风险。
- [ ] 已制作可恢复的备份。
- [ ] 已准备改动前后差异，而不是只给最终正文。
- [ ] 批量、删除、覆盖、执行脚本等高风险动作已获得人工确认。

### 写入时

- [ ] 只修改已批准的目标和范围。
- [ ] 冲突信息保留在正文或候选记录中，并说明采纳理由。
- [ ] 不顺手整理无关格式，不扩大改动面。
- [ ] 局部规则高于通用规则。

### 写入后

- [ ] 重新打开目标文件，确认内容与编码正常。
- [ ] 检查新增、改名或移动造成的链接影响。
- [ ] 按仓库规则维护对应 `index` 和 `log`。
- [ ] 记录谁批准、改了什么、如何回滚。
- [ ] 如果 LLMWiki 使用派生索引，再执行其已验证的重建流程；没有已验证流程时停下询问。

## 完成标准

- [ ] 来源、冲突、差异、审批与回滚都可追溯。
- [ ] 没有修改 `raw/`。
- [ ] 没有绕过 `index` 与 `log` 维护。
- [ ] 未出现未授权的连带修改。

## 常见错误

- 用“模型很确定”代替来源核验。
- 只展示改后结果，不展示差异。
- 批量写入后才询问用户是否同意。
- 正文写完就结束，忘记索引、日志和链接检查。
