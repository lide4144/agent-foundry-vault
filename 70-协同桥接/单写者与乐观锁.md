# 单写者与乐观锁

## 何时用

Obsidian 人工编辑、Hermes、LLMWiki、同步服务或多 Agent 可能同时接触同一文件时。

## 三步操作

1. 读取目标并计算 base_hash；候选阶段不占长期锁。
2. 单 writer 取出已批准任务，提交前重新计算 current_hash。
3. 哈希一致才原子写入；不一致进入 conflict，绝不覆盖。

## 单 writer 是什么

单 writer 不是“系统只能有一个用户”，而是同一时间只有一个提交者能把已批准差异写进正式路径。其他 Agent 可以并行读取、评测和生成候选，但不能并行提交同一文件。

## 乐观锁

~~~text
读取文件 → base_hash
生成候选与 diff
审批
提交前再次读取 → current_hash

base_hash == current_hash → 原子写入 → 回读验证
base_hash != current_hash → conflict → 重新合并与审批
~~~

## 实施要点

- 锁记录至少含 owner、candidate_id、目标路径、获取时间和 TTL。
- 锁文件只是协调信号，不是安全边界；真正边界仍是进程权限和单 writer 设计。
- 发现过期锁先检查 writer 是否仍运行，不能直接删锁后覆盖。
- 写入采用同目录临时文件、完成刷新后原子替换；失败时保留原文件。
- 页面、index.md 和 log.md 应属于同一变更集；不能三个 writer 分开提交。
- Obsidian 正在人工编辑目标时，Agent 自动提交应暂停并重新读取。

## 完成标准

- [ ] 每次正式提交有唯一 writer。
- [ ] base_hash 与 current_hash 已比较。
- [ ] 冲突未自动覆盖。
- [ ] 写后回读与链接检查通过。

## 常见错误

- 多 Agent 各自认为自己改的是不同段落。
- 把锁文件当 ACL。
- writer 崩溃后直接删除锁，不检查临时文件和部分提交。
